# Руководство для AI-агентов

## Обзор проекта

«Молния» — независимая пересборка официальных стабильных релизов [Zen Browser](https://github.com/zen-browser/desktop) на движке Firefox. Это **не исходники браузера и не форк с компиляцией Firefox/Zen**: репозиторий содержит инструменты, которые скачивают готовые артефакты Zen, изменяют их и упаковывают заново.

Продуктовые особенности:

- корневой и промежуточный сертификаты Минцифры поставляются вместе с браузером;
- русская локаль и регион `RU` задаются по умолчанию, поисковик по умолчанию — Яндекс;
- uBlock Origin и собственный детектор обновлений встраиваются как расширения;
- телеметрия, эксперименты и родной апдейтер Zen отключены;
- Safe Browsing и обновления расширений остаются включёнными;
- бренд Zen в интерфейсе заменяется на «Молния», а обязательная атрибуция Zen Browser и Mozilla сохраняется;
- выпускаются macOS `.dmg`, portable Windows `.zip` и Linux `.tar.xz`.

Основной язык документации, комментариев, сообщений об ошибках и названий тестов — русский. Идентификаторы в коде — английские.

## Технологии и зависимости

- Node.js **20 или новее**, ECMAScript modules (`package.json` содержит `"type": "module"`).
- Только стандартная библиотека Node.js; npm-зависимостей и lock-файла нет. `npm install` для работы не требуется.
- Внешние программы: `curl`, `7z`, `zip`, `unzip`, `xz`, `tar`.
- Для macOS дополнительно: `hdiutil`, `codesign`, `iconutil`; тесты macOS-идентичности используют также `plutil`.
- Детектор обновлений — Firefox WebExtension Manifest V2 на vanilla JavaScript.
- Лендинг — статические HTML/CSS/JavaScript без сборщика и фреймворков.
- CI и публикация — GitHub Actions и GitHub Releases; лендинг деплоится на VPS с Caddy (rsync по SSH).

На macOS недостающий `7z` обычно устанавливается через `brew install p7zip`. Полный локальный пайплайн рассчитан на macOS: Windows- и Linux-артефакты там собираются кросс-платформенно, а macOS-артефакт требует системных утилит Apple.

## Структура и модули

- `package.json` — Node.js-манифест и три npm-команды: `test`, `toolcheck`, `pipeline`.
- `src/config.mjs` — единый источник основных констант: бренд, upstream-репозиторий и имена ассетов, URL/SHA256-пины сертификатов и uBlock, параметры поиска, GitHub-координаты и рабочие каталоги.
- `src/fetch-upstream.mjs` — обращение к GitHub Releases API, строгий выбор точного имени ассета и скачивание через `curl`. Отсутствие ожидаемого файла вызывает `MissingAssetError` со списком доступных ассетов.
- `src/certs.mjs` — отдельный помощник для скачивания сертификатов Минцифры с `gu-st.ru` и проверки их SHA256; несовпадение вызывает `CertPinError`.
- `src/build-distribution.mjs` — создаёт `distribution/policies.json`, `distribution/Certificates/`, `distribution/extensions/`, `distribution/distribution.ini`, `molniya.cfg` и `defaults/pref/autoconfig.js`. Здесь же скачиваются и проверяются сертификаты/uBlock и упаковывается детектор в XPI.
- `src/patch-brand.mjs` — распаковывает и собирает `omni.ja`, заменяет строки и графические ассеты бренда, патчит `AppConstants.sys.mjs`, `application.ini`, а на macOS — `Info.plist`, `InfoPlist.strings` и имя исполняемого файла. `BuildID` обновляется при каждом патче, чтобы не оставался старый startup cache. `BrandResidueError` останавливает сборку при остаточном бренде в проверяемых строках.
- `src/repack-mac.mjs` — ad-hoc подпись `.app`, проверка подписи, создание и проверка DMG; также содержит общие функции имён артефактов и SHA256.
- `src/repack-win.mjs` — общий `patchInstallDir()` для Windows/Linux: distribution, бренд-omni и идентичность каталога установки; на Windows — PE-патчинг exe и плитки Пуска.
- `src/patch-win-exe.mjs` — патчер PE-ресурсов exe Windows: иконки Zen → Молния строго in-place без роста файла (BMP-кадры байт-в-байт по размеру слота, PNG-256 пишется только если влезает, иначе 256-кадр выбрасывается из группы), строки VERSIONINFO (Молния/molniya.exe; атрибуция Mozilla сохраняется). При нехватке места под VERSIONINFO выбрасывается мусорный RT_STRING. Синтетический мини-PE для тестов — `tests/helpers/win-pe.mjs`.
- `src/repack-linux.mjs` — переименование Linux-запускателя/корневого каталога и создание `tar.xz`.
- `src/pipeline.mjs` — CLI и оркестратор полного процесса: fetch → unpack → distribution → brand/identity → repack → checksum.
- `detector-extension/` — встроенное MV2-расширение. `lib/version.js` содержит чистую логику разбора и сравнения версий; `background.js` проверяет GitHub Releases при старте и раз в сутки, показывает бейдж/уведомление; `options.*` управляют включением проверок.
- `landing/` — сайт `molniya-browser.ru`: `index.html`, `thank-you-zen.html`, `style.css`, `app.js` и иконка. Кнопки ведут на общий `releases/latest`, а `app.js` подсвечивает вероятную ОС пользователя.
- `assets/branding/` — готовые SVG/PNG, копируемые в browser `omni.ja`; `assets/molniya.icns` — иконки macOS-бандла. `assets/candidates/` и `design/` — исходные/альтернативные дизайн-материалы, не часть runtime.
- `scripts/toolcheck.mjs` — проверка внешних программ; `scripts/check-links.mjs` — извлечение и HTTP HEAD-проверка внешних ссылок лендинга.
- `tests/` — тесты `node:test` с фикстурами во временных каталогах.
- `.github/workflows/release.yml` — ручная сборка и draft release; `.github/workflows/landing-deploy.yml` — деплой лендинга на VPS.
- `docs/spike-findings-mac.md` — наиболее подробная проверенная рецептура перепаковки; `docs/release-checklist.md` — обязательная ручная приёмка.
- `docs/superpowers/specs/` и `docs/superpowers/plans/` — исходный замысел и исторический план. Они полезны для контекста, но местами расходятся с текущей реализацией; при конфликте ориентируйтесь на код, README и финальные разделы spike-findings.
- `work/` и `dist/` — генерируемые и игнорируемые Git каталоги. Не редактируйте их содержимое как исходный код и не коммитьте артефакты.

## Архитектура сборки и runtime

### Общий поток

`runPipeline({ os, tag, workDir })` получает релиз `zen-browser/desktop` (конкретный тег или `latest`), строго выбирает нужный ассет и скачивает его в `work/upstream/`. Версия результата имеет вид `<zenTag>-molniya.N`, имя файла — `molniya-<version>-<os>.<ext>`.

Затем в установку добавляются:

- два сертификата в `distribution/Certificates/` с заглавной `C`; в `Certificates.Install` указываются только имена файлов;
- политики поиска Яндекс, закладок, отключения телеметрии/экспериментов/апдейтера и подавления first-run/post-update страниц;
- pref-only autoconfig с русской локалью, регионом и настройками приватности/безопасности;
- XPI uBlock Origin и детектора обновлений.

Брендинг выполняется в нескольких слоях: локали `.ftl/.dtd/.properties` в browser `omni.ja`, картинки из `assets/branding/`, скомпилированные константы в toolkit `omni.ja`, `application.ini` и платформенные метаданные. Не удаляйте атрибуцию Zen Browser/Mozilla: замена пользовательского бренда и сохранение атрибуции — разные требования.

### Платформенные различия

- **macOS:** DMG монтируется через `hdiutil`, `.app` копируется в `work/build/Молния.app`; ресурсы находятся в `Contents/Resources/`. Дополнительно заменяются ICNS, удаляется `Assets.car`, бинарник `zen` переименовывается в `molniya`. Перед подписью обязательно выполняется `xattr -cr`; затем ad-hoc `codesign`, `codesign --verify`, создание DMG и `hdiutil verify`.
- **Windows:** NSIS-инсталлятор целиком распаковывается `7z`; каталог `core/` переименовывается в `Molniya/`, патчится и архивируется в portable ZIP. Инсталлятор и реестр Windows не используются. Бинарник `zen.exe` переименовывается в `molniya.exe`; иконки и VERSIONINFO в `molniya.exe` и `private_browsing.exe` патчатся in-place (файл не растёт — раскладки BMP-слотов и палитровый `icon256.png` ≤ 16540 байт охраняются тестами); плитки Пуска `browser/VisualElements/` заменяются на `icon70/icon150.png`. ZIP-артефакт удаляется перед упаковкой: `zip` дополняет существующий архив, и в нём иначе остаются призраки переименованных файлов.
- **Linux:** upstream `tar.xz` распаковывается, корень установки патчится тем же `patchInstallDir()`, запускатель и корневой каталог получают имя `molniya`, затем создаётся новый `tar.xz`.

### Обновления

Родной апдейтер Zen должен оставаться отключённым: он может перезаписать пересборку. Детектор лишь сравнивает текущий тег с последним GitHub Release и предлагает ссылку на скачивание; сам браузер не обновляется. При сетевой ошибке или нераспознанном теге детектор молчит, повторное уведомление о той же версии подавляется через `storage.local`.

## Команды

Запускайте команды из корня репозитория: относительные пути к ассетам и `detector-extension/` рассчитаны на это.

```bash
# Проверить наличие внешних инструментов
npm run toolcheck

# Все unit-тесты
npm test

# Один тестовый файл
node --test tests/patch-brand.test.mjs

# Проверить внешние ссылки лендинга (реальные HTTP HEAD-запросы)
node scripts/check-links.mjs

# Полные сборки; скачивают большие upstream-артефакты и обращаются к gu-st.ru/AMO
npm run pipeline -- --os mac   --tag latest
npm run pipeline -- --os win   --tag latest
npm run pipeline -- --os linux --tag latest

# Конкретный тег Zen и альтернативный рабочий каталог
npm run pipeline -- --os mac --tag 1.24b --work work/custom
```

Результаты попадают в `dist/`, там же записывается `version.txt`. Локальный пайплайн **добавляет** строки в `dist/SHA256SUMS`; CI перед выпуском заново создаёт общий файл. Пайплайн удаляет и заново создаёт соответствующие рабочие каталоги (`work/build`, `work/win`, `work/linux`), поэтому не храните там ручные изменения.

Отдельных команд lint, format, dev-server или production build для лендинга нет. Не запускайте полный pipeline вместо unit-тестов для небольших изменений: это сетевая, долгая и деструктивная для рабочих каталогов операция.

## Стиль и соглашения разработки

- Используйте ESM-импорты/экспорты и API `node:*`; не добавляйте npm-зависимости без необходимости — текущая архитектура сознательно построена на stdlib и внешних утилитах.
- Соблюдайте существующий стиль: отступ в 2 пробела, одинарные кавычки в JavaScript, точки с запятой, `async`/`await`, явные имена функций.
- Пишите новые комментарии, пользовательские сообщения и названия тестов по-русски. Не добавляйте очевидных комментариев; сохраняйте пояснения к нестандартным механизмам Firefox/Zen.
- Общие конфигурационные значения держите в `CONFIG`, а не дублируйте по модулям. URL детектора в настоящее время заданы отдельно в его коде.
- Внешние команды запускаются через `spawnSync`; ненулевой код обычно превращается в понятное исключение. Сохраняйте fail-fast поведение: неполный или непроверенный артефакт не должен считаться успешной сборкой.
- Для сетевых зависимостей сохраняйте dependency injection (`downloads`, `download`, `fetchImpl`), чтобы unit-тесты не ходили в сеть.
- Имена выпускаемых файлов и CLI/путей — латиницей (`Molniya`, `molniya`); видимое название продукта — «Молния».
- Не переименовывайте файлы `zen-*.ftl` только ради брендинга: заменяются содержимое и пользовательские идентификаторы, а не безусловно все вхождения `zen` в путях.
- При изменении механики `omni.ja`, сертификатов, профилей, подписи или macOS-метаданных сверяйтесь с `docs/spike-findings-mac.md` и обновляйте документацию, если поведение изменилось.

## Тестирование и приёмка

Стандартная проверка перед завершением изменения:

```bash
npm test
node scripts/check-links.mjs   # если затронут лендинг или его ссылки; требует сети
npm run toolcheck             # при изменении требований к инструментам
```

В настоящее время `npm test` запускает 49 тестов из `tests/*.test.mjs`. Они используют `node:test`, `assert/strict`, временные каталоги и моки скачивания/fetch. Тесты патчинга и упаковки вызывают настоящие `7z`, `zip`, `tar` и связанные утилиты; PE-патчер тестируется на синтетическом мини-PE без настоящих exe; macOS-тест идентичности вызывает `plutil`, поэтому весь набор рассчитан прежде всего на среду разработки macOS.

Покрытые инварианты важно не ослаблять:

- отсутствие upstream-ассета и подмена сертификата/uBlock должны приводить к ошибке;
- сертификаты должны лежать именно в `Certificates/`, а политика содержать голые имена;
- телеметрия off, но Safe Browsing и обновления расширений on;
- бренд-строки и картинки заменяются, residue-контроль остаётся; в Windows-артефакте нет `zen.exe` — бинарник переименован, а PE-ресурсы (иконки, VERSIONINFO) не содержат Zen;
- `BuildID` меняется, артефакты и SHA256 имеют ожидаемый формат;
- детектор не уведомляет при offline, той же версии или повторном обнаружении;
- битые внешние ссылки лендинга обнаруживаются.

Unit-тесты не заменяют проверку реального браузера. Для изменений сборки выполняйте полный pipeline соответствующей ОС и ручной чек-лист `docs/release-checklist.md`: запуск, `about:policies`, доверие Russian Trusted Root CA и открытие Госуслуг, поиск, русский UI, брендинг, отключённый апдейтер, сосуществование с Zen и работу детектора. macOS также требует проверки подписи/DMG; Windows и Linux — запуска распакованного артефакта.

## Безопасность

- Сертификаты скачивайте только из закреплённых официальных URL `gu-st.ru`; uBlock — из настроенного AMO URL. SHA256-пины находятся в `src/config.mjs`.
- Не обновляйте пин автоматически вслед за изменившимся файлом. Сначала установите причину ротации и проверьте источник; затем осознанно измените URL/версию/хеш и прогоните тесты и ручную приёмку.
- Не включайте родной апдейтер Zen и не отключайте защитные проверки под предлогом приватности.
- `GITHUB_TOKEN` используется только для авторизации запросов к GitHub API в upstream-fetch/CI. Не записывайте токены, сертификаты с приватными ключами или другие секреты в репозиторий и логи.
- macOS-подпись является **ad-hoc**, Windows-артефакт не имеет vendor code signing. Не описывайте их как подпись Apple/Microsoft: Gatekeeper и SmartScreen могут предупреждать пользователя.
- SHA256SUMS обеспечивает контроль целостности выпущенных файлов. Проверка релиза: `shasum -a 256 -c SHA256SUMS` на macOS или `sha256sum -c SHA256SUMS` на Linux из каталога с артефактами.

## CI, релиз и деплой

Workflow `release` запускается вручную (`workflow_dispatch`) с входами `zen_tag` и `build_n`; `build_n` передаётся в pipeline как `--build` и задаёт суффикс версии `molniya.N`. Матрица собирает macOS на `macos-15` (arm64; `macos-14` выведен GitHub из поддержки), Windows и Linux на `ubuntu-24.04`; три артефакта и `version.txt` передаются в release-job. Последний пересчитывает общий `SHA256SUMS` и создаёт **draft** GitHub Release через `gh release create`.

После успешной матрицы и ручной приёмки draft публикуется человеком. Обновление uBlock выполняется вручную: проверить новый XPI, затем обновить `version` и `sha256` в `src/config.mjs`.

Workflow `landing-deploy` синхронизирует каталог `landing/` на VPS `46.19.68.175` (Caddy, корень `/var/www/molniya-browser.ru`) через rsync при push в `main` с изменениями в лендинге и при ручном запуске. Подключение идёт пользователем `deploy` с ключом из секрета `VPS_DEPLOY_KEY`; ключ ограничен на сервере принудительной командой `rrsync` и может только записывать файлы сайта. После синхронизации workflow проверяет, что `https://molniya-browser.ru` отвечает 200. Локальный rsync macOS (openrsync) несовместим с `rrsync` — синхронизацию проверяйте GNU rsync (Linux/CI).

## Текущие ограничения

- Несмотря на `Profile=molniya` в `application.ini`, фактический корень профиля macOS остаётся общим с Zen (`~/Library/Application Support/zen`) из-за значения в скомпилированном XUL. Последовательная работа поддерживается, одновременный запуск может показать штатный диалог занятого профиля; не заявляйте полную изоляцию профилей.
- Windows распространяется как portable ZIP без установщика и записей реестра; Linux — только `tar.xz`, без DEB/Flatpak.
- Русский langpack отдельно не скачивается: используется локаль, уже присутствующая в артефакте Zen.
- Автоматической установки обновлений, мобильных платформ, собственной синхронизации и ГОСТ-TLS в v1 нет.
